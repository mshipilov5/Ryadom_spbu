# API Documentation Rules

## 1. Назначение документа

Документ определяет правила документирования API веб-сервиса «Рядом».

Цели:
- обеспечить единое понимание API между frontend и backend;
- предоставить разработчикам полную информацию для интеграции;
- сократить количество ошибок, вызванных неоднозначностью контракта;
- обеспечить актуальность и проверяемость документации.

Правила распространяются на все публичные endpoints и изменения их контрактов.

## 2. Связь с правилами проектирования API

Документ определяет, как описывать API, но не устанавливает повторно правила его проектирования.

Требования к URL, HTTP-методам, форматам данных, обработке ошибок, безопасности и поведению API определяются в `api-design-rules.md`.

Конкретные маршруты, параметры, схемы запросов и ответов, коды состояния HTTP и требования к доступу определяются спецификацией OpenAPI.

При обнаружении противоречий между спецификацией и правилами проектирования необходимо согласовать изменения и устранить расхождения до принятия соответствующих изменений в основную ветку.

## 3. Swagger UI

Для просмотра спецификации и выполнения тестовых запросов рекомендуется использовать Swagger UI.

Swagger UI должен отображать актуальную версию OpenAPI.

Если проект использует генерацию серверного или клиентского кода, она должна выполняться на основе согласованной спецификации.

Генерация кода не заменяет проверку корректности контракта и тестирование реализации.

## 4. Структура описания endpoint

Каждый endpoint должен иметь описание, достаточное для использования API без изучения исходного кода backend.

Описание должно включать:

- название операции;
- назначение;
- HTTP-метод и путь;
- параметры пути и запроса;
- тело запроса, если оно предусмотрено;
- схемы успешных ответов;
- возможные ошибки;
- требования к аутентификации и авторизации;
- ограничения и особенности поведения;
- примеры запросов и ответов, когда они помогают понять контракт.

### 4.1. Название и назначение

Название операции должно кратко отражать её результат.

Описание должно объяснять:
- какую задачу решает endpoint;
- с каким ресурсом он работает;
- какие основные условия влияют на результат.

Не следует дублировать в описании внутреннюю реализацию обработчика.

### 4.2. Пример описания endpoint

Пример оформления операции в документации:

**Название:** Получение статьи.

**Метод:** GET.

**Endpoint:** `/api/v1/articles/{articleId}`.

**Назначение:** получение статьи по её идентификатору.

**Аутентификация:** не требуется, если статья относится к публичному содержимому.

**Параметры пути:**

| Параметр | Тип | Обязательный | Описание |
|---|---|---|---|
| articleId | string | Да | Идентификатор статьи |

**Успешные ответы:**

- `200 OK` — статья успешно получена.

**Возможные ошибки:**

- `404 Not Found` — статья не найдена.

Это пример структуры описания. Фактические параметры, статусы и требования к доступу определяются согласованным контрактом.

## 5. Документирование параметров

Для каждого параметра необходимо указывать:

- название;
- расположение: путь, строка запроса или заголовок;
- тип данных;
- обязательность;
- назначение;
- ограничения;
- допустимые значения;
- значение по умолчанию, если оно предусмотрено.

Для параметров, принимающих ограниченный набор значений, необходимо перечислять допустимые варианты.

Для числовых параметров указываются минимальные и максимальные значения, если они ограничены.

Для дат, идентификаторов и других параметров со специальным форматом необходимо указывать ожидаемый формат.

## 6. Документирование запросов

Для каждого endpoint, принимающего тело запроса, необходимо описать:

- структуру данных;
- обязательные и необязательные поля;
- типы данных;
- ограничения значений;
- правила валидации;
- допустимость `null`;
- поведение при отсутствии обязательных полей.

Пример создания статьи:

    POST /api/v1/articles

    {
      "title": "Как справляться со стрессом",
      "category": "stress",
      "content": "Описание материала"
    }

Описание полей:

| Поле | Тип | Обязательное | Описание |
|---|---|---|---|
| title | string | Да | Заголовок статьи |
| category | string | Да | Категория материала |
| content | string | Да | Содержание статьи |

Пример должен соответствовать схеме запроса, установленной в OpenAPI.

Если endpoint не принимает тело запроса, это следует явно указать, когда такая информация необходима для понимания операции.

## 7. Документирование ответов

### 7.1. Успешные ответы

Для каждого endpoint необходимо указать все предусмотренные варианты успешных ответов.

Для каждого варианта указываются:
- HTTP-статус;
- назначение;
- схема ответа;
- обязательные и необязательные поля;
- типы данных;
- ограничения значений.

Пример ответа:

    {
      "id": "article-123",
      "title": "Как справляться со стрессом",
      "category": "stress",
      "content": "Описание материала",
      "createdAt": "2026-10-17T12:00:00Z"
    }

Пример и схема должны соответствовать согласованным соглашениям API.

### 7.2. Коллекции ресурсов

Для endpoints, возвращающих коллекции, необходимо описать:

- структуру элемента коллекции;
- структуру ответа;
- параметры пагинации;
- метаданные пагинации, если они предусмотрены;
- поведение при отсутствии элементов.

Если коллекция использует обёртку `items` и объект `pagination`, их структура должна быть явно определена в спецификации.

Не следует придумывать разные форматы ответов для схожих endpoints без обоснованной причины.

### 7.3. Пустые ответы

Если операция возвращает ответ без тела, необходимо указать соответствующий HTTP-статус и явно обозначить отсутствие тела ответа.

## 8. Документирование ошибок

Для каждого endpoint необходимо перечислить применимые ошибки и условия их возникновения.

Документация должна позволять потребителю API определить:
- причину ошибки;
- необходимость изменения пользовательского ввода;
- необходимость повторной аутентификации;
- наличие или отсутствие прав доступа;
- возможность безопасного повторения запроса.

Формат тела ошибки определяется в `api-design-rules.md`.

Для каждой ошибки необходимо описать:
- HTTP-статус;
- схему ответа;
- назначение полей;
- условия возникновения;
- пример ответа, если он помогает понять контракт.

Не следует повторно определять формат ошибок в описании каждого endpoint. Общая схема должна быть переиспользована в OpenAPI.

## 9. Документирование аутентификации и авторизации

Для каждого endpoint необходимо указать:

- требуется ли аутентификация;
- какие роли или права необходимы;
- какие ограничения доступа применяются;
- какие ошибки могут возникнуть при отсутствии аутентификации или прав.

Для публичных endpoints следует явно указывать отсутствие требований к аутентификации, если это важно для потребителя API.

Описание должно соответствовать правилам доступа, установленным требованиями продукта и API Design Rules.

Не следует включать в документацию реальные токены, пароли, секреты или другие чувствительные данные.

## 10. Документирование пагинации, фильтрации и сортировки

Если endpoint поддерживает пагинацию, фильтрацию или сортировку, необходимо документировать все соответствующие параметры.

Для каждого параметра указываются:
- название и тип;
- назначение;
- обязательность;
- значение по умолчанию;
- ограничения;
- допустимые значения.

Для пагинации необходимо описать формат получения следующей страницы и структуру метаданных, если они предусмотрены контрактом.

Пример:

    GET /api/v1/articles?limit=20&offset=0

Для сортировки необходимо указывать поддерживаемые поля и допустимые направления.

Документация должна соответствовать выбранному для endpoint механизму пагинации и правилам API Design Rules.

## 11. Требования к примерам

Примеры должны:
- соответствовать актуальным схемам;
- использовать согласованные названия полей;
- содержать реалистичные тестовые данные;
- демонстрировать корректное использование параметров;
- не содержать реальных персональных данных, секретов или токенов;
- не противоречить описанию endpoint.

Примеры не должны представлять собой копии внутренних моделей базы данных, если они не совпадают с публичным контрактом.

Если пример содержит идентификаторы, даты или другие специальные значения, они должны соответствовать установленным форматам.

Примеры должны помогать понять использование API, а не заменять описание схем и ограничений.

## 12. Обновление документации

Документация обновляется одновременно с изменением API.

Разработчик, изменяющий контракт, обязан:

1. Обновить спецификацию OpenAPI.
2. Обновить затронутые схемы запросов и ответов.
3. Проверить применимые HTTP-статусы и ошибки.
4. Обновить примеры.
5. Проверить требования к аутентификации и авторизации.
6. Проверить влияние изменений на существующих потребителей API.
7. Включить изменения документации в тот же Pull Request, что и изменение контракта.

Если изменение влияет на frontend или другие компоненты, необходимо согласовать его до начала реализации.

Изменения публичного контракта не должны попадать в основную ветку без соответствующего обновления спецификации.

## 13. Проверка документации

Перед принятием изменений необходимо проверить:

- все изменённые endpoints отражены в OpenAPI;
- HTTP-методы и пути соответствуют согласованному контракту;
- параметры и схемы описаны полностью;
- обязательность полей указана корректно;
- примеры соответствуют актуальным схемам;
- успешные ответы и ошибки документированы;
- требования к доступу указаны корректно;
- спецификация проходит проверку используемым валидатором;
- изменения не создают противоречий с API Design Rules;
- документация не содержит секретов и реальных персональных данных.

При наличии автоматизированных тестов рекомендуется дополнительно проверять соответствие реализации спецификации.

## 14. Definition of Done документации API

Документирование endpoint считается завершённым, если:

- [ ] Назначение операции описано однозначно.
- [ ] Указаны HTTP-метод и путь.
- [ ] Описаны все параметры.
- [ ] Описано тело запроса, если оно предусмотрено.
- [ ] Указаны типы, обязательность и ограничения полей.
- [ ] Описаны успешные ответы и их схемы.
- [ ] Указаны применимые ошибки и HTTP-статусы.
- [ ] Документированы требования к аутентификации и авторизации.
- [ ] Добавлены необходимые примеры запросов и ответов.
- [ ] Спецификация соответствует API Design Rules.
- [ ] OpenAPI проходит проверку используемым валидатором.
- [ ] Изменения включены в Pull Request.
- [ ] Документация согласована с затронутыми участниками команды.

## 15. Итоговое правило

Документация API является частью результата разработки.

Endpoint не считается полностью документированным, если его контракт невозможно однозначно понять по OpenAPI или если спецификация противоречит согласованным правилам проектирования.

OpenAPI должна оставаться актуальным источником информации о конкретных endpoints, их параметрах, схемах запросов и ответов.
