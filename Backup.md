**1) Что копировать**

Для обеспечения полного восстановления работоспособности системы в случае сбоя необходимо резервировать следующие компоненты:

*   **База данных.** Логические дампы (полные и инкрементальные). Журналы транзакций (WAL) для возможности восстановления на любой момент времени (Point-in-Time Recovery).
*   **Файловое хранилище (Пользовательские данные).** Файлы, загруженные пользователями (аватары, документы, вложения). Если используется S3-совместимое хранилище (например, Yandex Object Storage), настраивается версионирование бакетов или их периодическая синхронизация. Если файлы хранятся в Docker volumes — резервируются соответствующие директории.
*   **Конфигурация и инфраструктура.** Файлы переменных окружения (.env, secrets). Конфигурационные файлы Nginx, Docker Compose и т.д. Инфраструктурный код (Terraform/Ansible манифесты), если применимо.

**2) Как часто**

Для production рекомендуется:

*   **База данных:**
    *   Полный дамп — ежедневно (в часы минимальной нагрузки).
    *   Инкрементальные копии / архивация WAL-журналов — каждый час (или чаще, в зависимости от нагрузки).
*   **Файлы:** Ежедневно (или непрерывная репликация, если используется S3).
*   **Конфигурация:** При каждом изменении (желательно хранить в Git).
*   **Перед обновлениями (релизами):** Обязательный внеплановый бэкап всех критичных данных перед деплоем новой версии.

**3) Куда складывать копии**

При организации хранения необходимо соблюдать принцип 3-2-1 (минимум 3 копии, на 2 разных носителях, 1 из которых — вне основной площадки).

*   **Основное хранилище:** Yandex Object Storage (S3) в отдельном бакете, изолированном от production-среды.
*   **Дополнительное хранилище:** Отдельный холодный диск (Cold Storage) или архивный класс хранения в Yandex Cloud для долгосрочных копий.

**Безопасность:**

*   Доступ к бакету с бэкапами должен быть строго ограничен (отдельный сервисный аккаунт).
*   Рекомендуется включить Object Lock (защита от удаления) для защиты от программ-вымогателей и случайного удаления.
*   Данные должны быть зашифрованы при передаче (TLS) и в состоянии покоя (шифрование бакета).

**4) Сколько хранить**

Для production применяется политика многоуровневого хранения (GFS — Grandfather-Father-Son). Минимальные рекомендуемые сроки:

*   **Ежедневные копии:** 30 дней.
*   **Еженедельные копии:** 3 месяца.
*   **Ежемесячные копии:** 1 год.
*   **Годовые копии:** До 3 лет (или согласно внутреннему регламенту компании).

**(152-ФЗ):** Если платформа обрабатывает персональные данные, сроки хранения резервных копий, содержащих ПДн, должны соответствовать требованиям законодательства РФ (обычно не менее 1 года). Хранение таких копий должно осуществляться на серверах, расположенных на территории РФ.

**5) Как восстановить**

1.  **Подготовка изолированной среды:**
    *   Развернуть чистую инфраструктуру (или использовать стенд для восстановления), чтобы не перезаписать текущие production-данные.
2.  **Восстановление базы данных:**
    *   Остановить приложение (контейнеры), чтобы избежать записи новых данных.
    *   Развернуть чистый инстанс БД.
    *   Восстановить последний полный дамп.
    *   Применить инкрементальные копии/WAL-журналы до нужной точки во времени.
3.  **Восстановление файлов:**
    *   Скачать архив из S3 или восстановить данные из снапшота.
    *   Разместить файлы в соответствующих volume-директориях или бакете.
4.  **Применение конфигурации:**
    *   Развернуть актуальные .env и конфигурационные файлы.
5.  **Запуск и проверка:**
    *   Запустить контейнеры (`docker compose up -d`).
    *   Проверить логи, доступность сервиса и целостность данных (Smoke-тесты).
