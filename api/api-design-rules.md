# API Design Rules

## 1. Назначение документа

Документ определяет общие правила проектирования API веб-сервиса «Рядом».

Цель — обеспечить единообразие API, упростить параллельную разработку frontend
и backend, снизить количество интеграционных ошибок и обеспечить возможность
дальнейшего развития системы.

Правила распространяются на все новые эндпоинты и изменения существующих.

Документ определяет принципы проектирования API.
Правила оформления спецификации OpenAPI описаны отдельно в
`docs/api-documentation-rules.md`.

## 2. Общие принципы

### 2.1. API-first

Перед реализацией нового эндпоинта необходимо согласовать его контракт.

Контракт должен определять:
- назначение эндпоинта;
- HTTP-метод и URL;
- параметры запроса;
- формат тела запроса;
- формат успешного ответа;
- возможные ошибки;
- требования к аутентификации и авторизации.

Контракт должен быть описан в OpenAPI до начала интеграции frontend и backend.

### 2.2. Единообразие

Все эндпоинты должны соответствовать общим правилам именования ресурсов,
использования HTTP-методов, передачи данных и обработки ошибок.

Отступления от установленных соглашений должны быть обоснованы и согласованы
с ответственными за проектирование API.

### 2.3. Независимость от реализации

Публичный контракт API не должен зависеть от внутренней структуры Go-пакетов,
моделей базы данных или деталей реализации бизнес-логики.

Изменения внутренней реализации не должны приводить к изменению API,
если внешнее поведение системы остаётся прежним.

### 2.4. Минимальная необходимая функциональность

Каждый эндпоинт должен решать конкретную задачу.

Не следует добавлять параметры, поля и операции без обоснованной необходимости.

## 3. Структура URL

### 3.1. Общие правила

Для URL используются следующие соглашения:
- префикс `/api/v1` для API первой версии;
- латиница в нижнем регистре;
- дефис `-` для разделения слов;
- существительные для обозначения ресурсов;
- множественное число для коллекций ресурсов;
- идентификаторы ресурсов передаются в пути URL.

Примеры:

- `GET /api/v1/articles`
- `GET /api/v1/articles/{articleId}`
- `POST /api/v1/appointments`
- `GET /api/v1/crisis-resources`

Не рекомендуется включать HTTP-методы или действия в названия URL.

Не рекомендуется:

- `/api/v1/getArticles`
- `/api/v1/createAppointment`
- `/api/v1/deleteArticle`

### 3.2. Вложенные ресурсы

Вложенные URL допустимы, если они отражают понятную связь между ресурсами.

Пример:

`GET /api/v1/users/{userId}/appointments`

Не следует создавать чрезмерно вложенные URL.

Если ресурс имеет собственный идентификатор и может запрашиваться независимо,
предпочтительно использовать отдельный маршрут.

### 3.3. Версионирование

Для API используется версионирование через URL:

`/api/v1/...`

Изменения, нарушающие обратную совместимость, требуют согласования
и определения стратегии перехода на новую версию API.

## 4. HTTP-методы

Каждый эндпоинт должен использовать HTTP-метод в соответствии с семантикой
выполняемой операции.

| Метод | Назначение |
|---|---|
| GET | Получение ресурса или коллекции ресурсов |
| POST | Создание ресурса или выполнение операции |
| PUT | Полная замена ресурса |
| PATCH | Частичное изменение ресурса |
| DELETE | Удаление ресурса |

Примеры:

- `GET /api/v1/articles`
- `GET /api/v1/articles/{articleId}`
- `POST /api/v1/articles`
- `PUT /api/v1/users/{userId}/profile`
- `PATCH /api/v1/users/{userId}/profile`
- `DELETE /api/v1/articles/{articleId}`

Правила:
- GET не должен изменять состояние системы.
- PUT должен иметь предсказуемое поведение при повторном выполнении.
- PATCH должен изменять только предусмотренные контрактом поля.
- DELETE должен иметь определённую семантику повторного вызова.
- POST применяется для создания ресурсов и операций, не подходящих под
  семантику остальных методов.

## 5. Формат данных

### 5.1. JSON

Для обмена структурированными данными используется JSON.

Для JSON-запросов и ответов применяется заголовок:

`Content-Type: application/json`

Если эндпоинт принимает другой формат, это должно быть явно определено
в контракте.

### 5.2. Именование полей

В JSON используется `camelCase`.

Пример:

{
  "id": "article-123",
  "title": "Как справиться со стрессом",
  "createdAt": "2026-10-17T12:00:00Z"
} 

### 5.3. Идентификаторы

Формат идентификаторов должен быть единообразным для одного типа ресурса.

Формат внешнего идентификатора определяется архитектурой проекта.

API не должен без необходимости раскрывать внутренние идентификаторы и детали организации базы данных.

### 5.4. Даты и время

Для передачи даты и времени используется формат RFC 3339.

Пример:

`2026-10-17T12:00:00Z`

Для моментов времени необходимо указывать часовой пояс или смещение.

Для функций, зависящих от местного времени, правила обработки часовых поясов должны быть явно определены.

### 5.5. Отсутствующие значения

Для каждого поля необходимо определить:

- обязательно ли оно;
- может ли оно отсутствовать;
- допускает ли оно значение `null`;
- допустимо ли пустое значение.

Для PATCH необходимо определить семантику отсутствующего поля и `null`.

Рекомендуемое соглашение:

- поле отсутствует — значение не изменяется;
- поле передано со значением — значение обновляется;
- поле передано как `null` — значение очищается, если это разрешено контрактом.

Конкретная семантика должна быть указана в контракте.

## 6. Формат ответов

Каждый эндпоинт должен иметь явно определённую схему успешного ответа.

Пример ответа при получении статьи:

{
  "id": "article-123",
  "title": "Как справиться со стрессом",
  "content": "Содержание статьи",
  "createdAt": "2026-10-17T12:00:00Z"
}

Обёртка `items` и объект `pagination` применяются к коллекциям, для которых выбран соответствующий формат ответа.

Не требуется оборачивать каждый ответ в общий объект, если это не нужно для единообразия или функциональности API.

Формат ответа должен быть согласован до реализации frontend и backend.

## 7. Обработка ошибок

### 7.1. Общие правила

Ошибки должны обрабатываться единообразно.

API не должен возвращать HTTP 200 в случае неуспешного выполнения операции.

Для ошибок рекомендуется использовать формат RFC 9457 (Problem Details for HTTP APIs) с типом содержимого `application/problem+json`.

Пример:

    {
      "type": "about:blank",
      "title": "Validation error",
      "status": 400,
      "detail": "The request contains invalid fields.",
      "code": "VALIDATION_ERROR"
    }

Поле `code` используется как стабильный машинный идентификатор ошибки, если оно предусмотрено общим контрактом.

### 7.2. HTTP-статусы

| Статус | Назначение |
|---|---|
| `200 OK` | Успешный запрос с телом ответа |
| `201 Created` | Ресурс успешно создан |
| `202 Accepted` | Запрос принят для асинхронной обработки |
| `204 No Content` | Успех без тела ответа |
| `400 Bad Request` | Некорректный запрос |
| `401 Unauthorized` | Требуется аутентификация |
| `403 Forbidden` | Недостаточно прав |
| `404 Not Found` | Ресурс не найден |
| `409 Conflict` | Конфликт состояния или ограничений |
| `422 Unprocessable Content` | Нарушены правила обработки корректно сформированного запроса |
| `429 Too Many Requests` | Превышен допустимый лимит запросов |
| `500 Internal Server Error` | Непредвиденная внутренняя ошибка |
| `503 Service Unavailable` | Сервис временно недоступен |

Для каждого эндпоинта необходимо определить реально применимые статусы.

### 7.3. Защита внутренних данных

Ответы об ошибках не должны содержать:

- stack trace;
- SQL-запросы;
- внутренние пути файловой системы;
- секреты и токены;
- технические сведения, позволяющие атаковать систему.

Подробная информация об ошибке может сохраняться в серверных логах с соблюдением требований безопасности.

## 8. Валидация данных

Все входные данные должны проверяться на стороне backend.

Валидация включает:

- обязательность полей;
- типы данных;
- длину строк;
- диапазоны числовых значений;
- допустимые значения перечислений;
- корректность идентификаторов и дат;
- соблюдение бизнес-ограничений.

Frontend-валидация не заменяет backend-валидацию.

При ошибке сервер должен возвращать предусмотренный контрактом статус и понятное описание проблемы.

Валидация должна выполняться до передачи данных в бизнес-логику, если это соответствует архитектуре конкретного обработчика.

## 9. Аутентификация и авторизация

### 9.1. Разделение понятий

Аутентификация определяет личность пользователя.

Авторизация определяет, какие ресурсы и операции ему доступны.

Успешная аутентификация не означает автоматического предоставления доступа ко всем ресурсам.

### 9.2. Гостевой доступ

Публичные эндпоинты должны быть явно определены.

Например, если требования продукта предусматривают публичный доступ к материалам и кризисным ресурсам:

- `GET /api/v1/articles`
- `GET /api/v1/crisis-resources`

Персональные операции должны требовать аутентификацию в соответствии с требованиями продукта.

### 9.3. Проверка прав доступа

Backend обязан проверять права доступа при каждом запросе к защищённому ресурсу.

Нельзя предоставлять доступ к пользовательским данным только на основании того, что клиент знает идентификатор пользователя или ресурса.

Должны проверяться принадлежность ресурса пользователю, необходимые роли и другие предусмотренные правилами доступа условия.

### 9.4. Персональные данные

API должен возвращать только те персональные данные, которые необходимы для выполнения конкретной функции.

Для персональных и чувствительных данных необходимы строгие проверки доступа и минимизация передаваемой информации.

## 10. Пагинация, фильтрация и сортировка

Для потенциально больших коллекций необходимо предусматривать пагинацию.

Пример:

`GET /api/v1/articles?limit=20&cursor=abc123`

Правила:

- `limit` определяет максимальное количество элементов в ответе;
- сервер ограничивает максимально допустимое значение `limit`;
- курсор обрабатывается сервером;
- формат следующей страницы описывается в контракте;
- фильтры и сортировка используют согласованные параметры.

Пример:

`GET /api/v1/articles?category=stress&sort=-createdAt&limit=20`

Соглашение `sort=-createdAt` означает сортировку по убыванию, если именно такая семантика закреплена в контракте.

Пагинация не обязательна для небольших фиксированных справочников.

## 11. Идемпотентность

API должен учитывать возможность повторной отправки запросов.

Правила:

- GET не должен изменять состояние системы;
- повторный PUT с одинаковыми данными должен приводить к эквивалентному состоянию;
- поведение повторного DELETE должно быть определено;
- для критически важных операций создания необходимо предотвращать нежелательное дублирование.

Для операций, где повторное выполнение может создать дубликаты, может применяться механизм идемпотентности, если он согласован контрактом.

Например, повторная отправка запроса на создание записи не должна приводить к нежелательному созданию нескольких одинаковых записей.

## 12. Безопасность

При проектировании API необходимо учитывать следующие требования:

- использование HTTPS в рабочих окружениях;
- проверка входных данных на сервере;
- проверка прав доступа к каждому защищённому ресурсу;
- ограничение размера тела запроса;
- защита от несанкционированного доступа к чужим объектам;
- ограничение частоты чувствительных операций;
- отсутствие секретов в URL;
- отсутствие секретов и токенов в логах;
- безопасная обработка ошибок;
- минимизация передаваемых персональных данных.

Для API, использующего cookies для сессий, отдельно определяются требования к CSRF-защите и настройкам cookies.

CORS должен быть настроен для разрешённых источников в соответствии с архитектурой развёртывания.

## 13. Обратная совместимость

Изменения API не должны без необходимости нарушать работу существующих клиентов.

Потенциально совместимые изменения:

- добавление нового эндпоинта;
- добавление необязательного параметра;
- добавление нового поля ответа при условии, что клиенты допускают неизвестные поля.

Потенциально несовместимые изменения:

- удаление существующего поля;
- изменение типа поля;
- изменение смысла параметра;
- изменение структуры ответа;
- изменение поведения существующего эндпоинта;
- изменение требований к авторизации.

Перед несовместимыми изменениями необходимо согласовать последствия, стратегию миграции и, при необходимости, новую версию API.

## 14. Логирование и наблюдаемость

Для диагностики API рекомендуется фиксировать:

- HTTP-метод и маршрут;
- HTTP-статус;
- длительность обработки;
- идентификатор корреляции запроса;
- внутренний код ошибки при её возникновении.

Логи не должны содержать пароли, токены, секреты и ненужные персональные данные.

Подробности внутренних ошибок должны быть доступны только уполномоченным лицам.

## 15. Тестирование

Для каждого нового эндпоинта необходимо определить тестовые сценарии.

Минимальный набор:

- успешный запрос;
- некорректные входные данные;
- отсутствие аутентификации;
- недостаточные права доступа;
- отсутствие ресурса;
- конфликт бизнес-правил;
- проверка формата ответа;
- проверка HTTP-статусов;
- проверка повторных запросов, если это применимо.

Для критичных операций дополнительно проверяются граничные случаи и конкурентное выполнение запросов.

## 16. Definition of Done для эндпоинта

Эндпоинт считается готовым, если:

- Назначение и поведение согласованы.
- Контракт OpenAPI согласован.
- HTTP-метод и URL соответствуют правилам.
- Определены схемы запросов и ответов.
- Определены возможные ошибки и HTTP-статусы.
- Реализована серверная валидация.
- Реализованы необходимые проверки доступа.
- Ошибки обрабатываются безопасно.
- Добавлены необходимые автоматизированные тесты.
- Реализация соответствует контракту.
- Документация обновлена.
- Изменения прошли code review.

## 17. Изменение правил

Изменения этого документа должны проходить code review.

Если изменение влияет на существующие API-контракты, необходимо оценить его влияние на frontend, backend и автоматизированные тесты.

При необходимости изменения правил согласовываются командой проекта.
